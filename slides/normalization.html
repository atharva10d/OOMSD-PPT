Data Modelling

Database Normalization (up to 3NF)

Structuring relational tables to eliminate data redundancy and prevent update anomalies.

STEP

01

First Normal Form

1NF

Flattened the composite Name attribute into atomic Fname and Lname columns.

Eliminated multi-valued attributes via dedicated intersection tables — TA_Certifications, Crew_Languages, Flight_Days.

1NF Schema View

-- Atomic Columns
UserID | Fname | Lname

-- Intersection Table
CREATE TABLE Crew_Languages (
  UserID INT,
  LanguageCode VARCHAR(10),
  PRIMARY KEY (UserID, LanguageCode)
);

STEP

02

Second Normal Form

2NF

Ensured all non-key attributes fully depend on the entire primary key.

In the Assigned_To table, AssignmentDate depends on the pairing of FlightID + UserID — not just one of them.

2NF Schema View

-- Fully dependent on Composite PK
CREATE TABLE Assigned_To (
  FlightID INT,
  UserID INT,
  AssignmentDate DATE, -- Depends on both
  PRIMARY KEY (FlightID, UserID)
);

-- Non-key attributes like 'CrewRole'
-- would not go here if they only depend
-- on UserID!

STEP

03

Third Normal Form

3NF

Removed transitive dependencies to prevent data corruption.

AvailableSeats is calculated dynamically (TotalSeats − Reservations) rather than stored physically.

TotalCost is locked in Reservation as a historical fact — protected from future Flight.Price changes.

3NF Schema View

-- No Transitive Dependencies
CREATE TABLE Reservation (
  ResID INT PRIMARY KEY,
  FlightID INT,
  TotalCost DECIMAL, -- Stored as fact
  FlightBasePrice -- Removed!
);

-- AvailableSeats is NOT stored.
-- It is derived dynamically via COUNT()
